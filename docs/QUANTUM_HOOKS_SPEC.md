# Quantum Hooks — on-chain specification

Quant Pad launches coins through pump.fun on Solana. pump.fun mints cannot carry Token-2022
transfer hooks and trades cannot be intercepted, so **Quantum Hooks are powered by the coin's
creator-fee stream**. At launch the coin's pump.fun `creator` is set to a per-mint PDA of the
`quantum_hooks` program (the **well**). Creator fees from the bonding curve (and from the canonical
PumpSwap pool after graduation) accumulate in the well and are routed by immutable, per-coin rules.

Program: Anchor **0.31.1**, Rust, program name `quantum_hooks`. Mint decimals are 6 and pump.fun
`create_v2` mints are Token-2022 (coins made with pump.fun's legacy `create` are SPL Token); all
token CPIs use the token interface and `transfer_checked`.

## Modules

| Module            | Effect                                                                                                               |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Creator share** | Share of each pulse paid to the launcher (optionally split, see Superposition).                                      |
| **Superposition** | Up to 4 extra wallets receive fixed shares of the creator slice.                                                     |
| **Quantum Burn**  | Reserve that buys the coin (curve or PumpSwap) from the well and burns every token.                                  |
| **Entanglement**  | Reserve distributed to holders by merkle epochs posted by the keeper.                                                |
| **Fusion**        | Reserve that, after graduation, adds liquidity to the canonical PumpSwap pool; LP locked forever (no withdraw path). |
| **Time Dilation** | Locks the launcher's dev-buy tokens with a cliff and linear vesting.                                                 |

Allocation bps (`creator_bps + burn_bps + entangle_bps + fusion_bps`) must equal 10 000 and are
**immutable after registration**. A protocol cut (`config.protocol_bps`, hard cap 1 000) is taken
from each pulse before allocation and paid to `config.treasury`.

## Instructions

1. **`initialize_config(treasury, keeper, protocol_bps, max_burn_lamports, min_action_interval, keeper_grace, claim_delay)`** — signer becomes `authority`. Once. `claim_delay` is 0..=604 800 s (clients default to 21 600 = 6 h); `version = 0`.
2. **`update_config(expected_version, treasury, keeper, protocol_bps, max_burn_lamports, min_action_interval, keeper_grace, claim_delay, new_authority)`** — authority only. Fails with `ConfigChanged` unless `config.version == expected_version`, then rewrites those fields and bumps `version`. It never touches `paused`. `protocol_bps ≤ 1000`. The client (`buildUpdateConfigInstruction`) fills unchanged fields and `expected_version` from the config it reads when building, so an update prepared before a pause, a keeper rotation or any other change fails instead of undoing it.
   **`set_paused(paused)`** — authority only; the only way to pause or unpause. Takes no expected version (an emergency pause always lands) and bumps `version`. A pause stops `register`, `quantum_burn` and `fusion` and nothing else (see `paused` under Implementation notes).
3. **`register(params)`** — accounts: `launcher` (signer, mut), `mint` (**signer**, must have 0 lamports and 0 data: a fresh mint keypair), `config`, `quantum` (init), `well` (mut, PDA), `system_program`. Validates bps sum = 10 000, `split_count ≤ 4`, split bps sum ≤ 10 000, no duplicate split wallets, lock parameters (`cliff ≤ duration`, `duration ≤ 4 years`). A split wallet must be an account `pulse` can pay, so it fails with `InvalidSplitWallet` when it is the default key, the well, the `Quantum` account, a sysvar, builtin or loader program (the `RESERVED_ACCOUNT_KEYS` list in `constants.rs`: keys the runtime never lets a transaction write-lock), this program, pump.fun (`6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P`) or PumpSwap (`pAMMBay6oceH9fJKBRHGP5D4bD4sWpmSwMn52FMfXEA`). Funds the well to the rent-exempt minimum from the launcher. Rejects when `config.paused`.
   A create_v2 + dev-buy transaction alone is ~1 224/1 232 bytes even with a lookup table, so a launch is up to **three transactions**, sent in order with one wallet prompt each (the next is simulated and shown only once the one before it confirmed; the wallet signs before the mint keypair): (A) `register` (launcher + mint keypair sign; the coin does not exist yet, so nothing can be sniped), (B) pump.fun `create_v2` with `creator = well` plus the optional dev buy, (C) the optional `lock`. `register` does not introspect the transaction for `create_v2`: requiring the fresh mint keypair's signature is what binds the config to whoever creates the coin, so nobody can register hooks for someone else's mint. If (B) never lands, the launcher can retry it with the same mint keypair. Clients should still check `bonding_curve.creator == well` before presenting a coin as Quantum. `params.lock` (optional `{cliff_secs, duration_secs}`) commits the Time Dilation terms; `lock` must then use exactly those terms. `last_burn_at` and `last_fusion_at` start at `created_at`, so the burn grace counts from launch (and then from the last burn); the public Fusion grace counts from the later of the last fusion and `graduated_at` (see item 11).
4. **`lock(amount, cliff_secs, duration_secs)`** — launcher only, once (`locked_amount == 0`). Transfers `amount` tokens from the launcher's Token-2022 ATA into the lock ATA (created idempotently). Sets `lock_start = now`, `lock_cliff = now + cliff`, `lock_end = now + duration`. Runs after the pump.fun dev buy, in its own transaction (C).
5. **`release()`** — launcher only. Vested = `locked × min(1, (now − start)/(end − start))`, zero before the cliff. Transfers `vested − released`.
6. **`pulse()`** — permissionless. Accounts: `rent_payer` (first account, writable signer), `config`, `quantum`, `well`, `treasury`, `launcher`, optional well WSOL ATA and SPL Token program, optional `bonding_curve` and `pool` (the coin's pump.fun curve and canonical PumpSwap pool, address-checked, read only), `system_program`. If the well WSOL ATA is present and initialized it is closed into the well first (native close moves all lamports). The ATA's rent, `rent.minimum_balance(165)` (2 039 280 lamports, capped at the amount closed), is refunded from the well to `rent_payer`, because the PumpSwap collect leg created the ATA at the transaction payer's expense; only the rest counts as unwrapped fees. If `graduated_at == 0` and the passed curve is complete or the passed pool exists, `graduated_at = now` (the client passes them only until then). Then
   `available = well.lamports − rent_min − (burn_reserve + entangle_reserve + entangle_owed + fusion_reserve + owed)`, where `owed = Σ split_owed + launcher_owed + protocol_owed`.
   Below 1 000 000 lamports nothing new is allocated (the refunded rent never counts, so the floor applies to fees only); the pulse then only pays owed amounts and fails with `NothingToPulse` if there are none it can pay. Otherwise `protocol = available × protocol_bps / 10 000` → treasury. `net = available − protocol`. Burn, entangle and fusion reserves increase by their bps of `net`; the creator slice is the remainder (absorbs rounding). Each split receives its bps of the creator slice; the launcher receives the rest. All transfers are system transfers signed by the well. **Owed ledger:** for the treasury, each split and the launcher the pulse pays `owed + share` in one transfer when the recipient can hold it (it would end at or above its rent-exempt minimum and is not executable); otherwise the share is added to that recipient's owed ledger, which stays reserved in the well and is never allocated again. So a recipient with an empty wallet loses nothing however many small pulses run; it is paid in full (owed first) by the first pulse after it can receive, including a pulse with no new fees. Split wallets are passed in `remaining_accounts` in stored order and must match, writable. A split account may be read-only only if it is a reserved key or executable (the runtime demotes those to read-only and they can never be paid); such a share is not owed (it could never be paid) but stays in the well unledgered and is allocated again by the next pulse (`register` refuses such wallets, so only coins registered before that check could have one). An ordinary wallet passed read-only fails with `SplitAccountsMismatch`, so a caller cannot push a real split's share into deferral. `Pulsed` reports `unwrapped` (fees only), `rent_refunded`, the amounts paid (`protocol`, `launcher_paid`, `splits_paid`, owed payments included), `owed_paid` and `deferred` (shares newly owed or left unledgered).
   The keeper transaction places pump.fun `sweep_creator_fee` + `collect_creator_fee` (curve) or PumpSwap `sweep_creator_fee` + `collect_coin_creator_fee` (pool, paying WSOL into the well WSOL ATA) **before** `pulse` in the same transaction; the program itself does not CPI into collection.
7. **`quantum_burn(spend: u64, cpi_data: Vec<u8>)`** — keeper only, or anyone when `now > last_burn_at + keeper_grace`. Also requires `now ≥ last_burn_at + min_action_interval` and `spend ≤ min(burn_reserve, max_burn_lamports)`. Accounts: `quantum`, `config`, `well`, `mint`, `well_token_ata` (init_if_needed), `token_program` (the coin mint's owner: Token-2022 for `create_v2` coins, SPL Token for coins created with pump.fun's legacy `create`), `instructions_sysvar` (`Sysvar1nstructions…`), `target_program`, plus `remaining_accounts` for the buy CPI.
   - **Public fallback** (caller ≠ `config.keeper`): `spend ≤ max_burn_lamports / 10`; the instruction must be invoked at the top level (stack height 1, no wrapper program); and every other top-level instruction of the transaction, read from the Instructions sysvar, must belong to this program, Compute Budget, System, SPL Token, Token-2022 or the Associated Token program, or be pump.fun / PumpSwap `init_user_volume_accumulator` (the client adds it when the well's accumulator is missing). Anything else, in particular any pump.fun / PumpSwap / pump-fee trade or a router, fails with `PublicTransactionNotAllowed`. The keeper path is unchanged.
   - `target_program` must be pump (`6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P`) or PumpSwap (`pAMMBay6oceH9fJKBRHGP5D4bD4sWpmSwMn52FMfXEA`).
   - The first 8 bytes of `cpi_data` must be a buy discriminator of that program (computed as `sha256("global:<name>")[..8]` and checked against the IDL in `@pump-fun/pump-sdk`). Allowed pump names: `buy`, `buy_exact_sol_in`, `buy_v2`, `buy_exact_quote_in_v2`, `buy_v3`, `buy_exact_quote_in_v3`. Allowed PumpSwap names: `buy`, `buy_exact_quote_in`, `buy_v2`, `buy_exact_quote_in_v2` (only those that exist in the IDL).
   - `quantum.mint` must appear in the CPI accounts; the well is the only signer PDA passed.
   - PumpSwap route: the program wraps `spend` into the well WSOL ATA (system transfer + `sync_native`), invokes, then closes the WSOL ATA back into the well.
   - `spent = well_before − well_after` (lamports, after unwrapping) must be ≤ `spend`. All tokens in the well token ATA are then burned (`burn` through `token_program`, well signs). `burn_reserve −= spent`, totals updated, `last_burn_at = now`. A burn through the canonical pool also records `graduated_at` if unset.
8. **`post_entanglement(root, total, leaf_count)`** — keeper only. `total ≤ entangle_reserve`, `1 ≤ leaf_count ≤ 16 384`, and `now ≥ last_epoch_at + 20 h` (`EpochTooSoon`; one epoch per coin per 20 hours). Creates `Epoch[epoch_count]` with `claim_start = now + config.claim_delay` and `expires_at = now + 30 days`, moves `total` from `entangle_reserve` to `entangle_owed`, `epoch_count += 1`, `last_epoch_at = now`.
9. **`claim_entanglement(index, leaf_index, amount, proof)`** — claimant signs. Leaf = `sha256(0x00 ‖ leaf_index u32 LE ‖ claimant ‖ amount u64 LE)`; inner nodes = `sha256(0x01 ‖ min(a,b) ‖ max(a,b))` (sorted pairs). Checks bitmap, sets bit, transfers `amount` from the well. Rejected before `claim_start` (`ClaimNotOpen`) and from `expires_at` (`EpochExpired`), so the claim window is `[created_at + claim_delay, created_at + 30 days)`.
10. **`close_epoch(index)`** — anyone after `expires_at`. Unclaimed (`total − claimed`) returns from `entangle_owed` to `entangle_reserve`; rent returns to `epoch.payer`.
    **`cancel_epoch(index)`** — `config.authority` only, while `now < claim_start` (`CancelWindowClosed` after). Returns `total − claimed` (the whole total: nothing can be claimed yet) from `entangle_owed` to `entangle_reserve` and closes the epoch, its rent going to `config.keeper` (the account that pays epoch rent). The index stays used and `last_epoch_at` is not reset, so the next epoch still waits out the 20 h interval. Emits `EpochCancelled { mint, index, returned, rent_to }`.
11. **`fusion(spend: u64, buy_data: Vec<u8>, buy_account_count: u8, deposit_data: Vec<u8>)`** — same gating as burn (shares `min_action_interval` via `last_fusion_at`) and the same public-fallback rules (spend cap, top level, no other trading instruction), except that the public grace counts from `max(last_fusion_at, graduated_at)`: anyone may fuse only when `now > max(last_fusion_at, graduated_at) + keeper_grace`. A fusion that finds `graduated_at` unset sets it to `now` first, so a public fusion can never be the first to record graduation. PumpSwap only. First CPI buys base with part of the wrapped SOL (`buy_*` discriminator), second CPI is PumpSwap `deposit` (discriminator check) with the well as user; remaining_accounts are split at `buy_account_count`. `token_program` is the coin mint's owner (Token-2022, or SPL Token for legacy `create` coins), as in `quantum_burn`; `lp_token_program` (Token-2022) is the token program of the pool's LP mint and the well LP ATA. LP tokens stay in the well LP ATA forever. Leftover base tokens are burned; leftover WSOL is unwrapped. `fusion_reserve −= spent`.

All state-changing instructions emit Anchor events (`ConfigUpdated`, `Registered`, `Locked`, `Released`, `Pulsed`, `Burned`, `EpochPosted`, `Claimed`, `EpochClosed`, `EpochCancelled`, `Fused`) with the mint and amounts.

## Trust model (documented to users)

- pump.fun's admins can reassign a coin's creator (`admin_cto`, `set_creator`), which would redirect future fees away from the well. Quant Pad cannot prevent this.
- pump.fun programs are upgradeable and change frequently; the discriminator allow-list must be kept current.
- This program needs an independent audit before holding meaningful value on mainnet.
- **The keeper key is hot** (it signs from the internet-facing server). It posts Entanglement roots and has priority on burns and fusions. The program does not check that a root matches holders, so the limits below are what stand between a leaked keeper key and the wells:
  - **What a leaked keeper key can do:** post, for each coin, one epoch per 20 hours whose root pays itself up to that coin's whole Entanglement reserve (at most about a day of accrual, since the keeper normally distributes daily), which also uses up that coin's 20-hour posting slot, delaying honest distributions until the key is rotated; run burns and fusions at a price it chooses (sandwiching them), each up to `max_burn_lamports` per coin every `min_action_interval`; spend its own SOL on epoch rent and fees.
  - **What it cannot do:** claim from an epoch before `claim_start` (`claim_delay`, default 6 hours, after the post); post a second epoch for a coin within 20 hours (so it cannot re-post after a cancel); touch burn or fusion reserves except through capped buys whose tokens are burned or whose LP stays in the well; move the treasury, launcher, split or owed payments; change the config, pause or unpause, or cancel epochs (authority only); withdraw SOL any other way.
  - **Claim delay and cancel window:** every epoch's claims open `claim_delay` after it is posted. Until then the authority can `cancel_epoch` it: its whole total returns to the coin's Entanglement reserve. Watching posted roots against the server's own records and cancelling a bad one (then rotating the keeper with `update_config`) inside the window means a leaked key gets nothing from Entanglement. The authority can set `claim_delay` from 0 (no window; not recommended) to 7 days. Claims stay open until 30 days after the post. `scripts/program-ops.mjs --epochs <mint>` lists a coin's epochs and which can still be cancelled; `--cancel-epoch <mint> <index>`, `--pause` / `--unpause` and the `update_config` flags build, check and simulate the authority instructions (a dry run unless `--yes`; `--authority-pubkey` prints the instruction for a multisig proposal instead).
- **Public fallback limits.** Anyone may run a burn after `keeper_grace` without a keeper burn, and a fusion after `keeper_grace` from the later of the last fusion and the coin's graduation (so a coin that graduates long after launch still gives the keeper a full grace for its first fusion). A public caller chooses the price limits inside the CPI data, so its run can be sandwiched; to bound that, it may spend at most `max_burn_lamports / 10` per action, must call the program at the top level, and its transaction may contain no other trading instruction (only Compute Budget, System, token, associated-token and Quantum Hooks instructions, plus the pump.fun / PumpSwap volume-accumulator init). This blocks sandwiches inside the same transaction, including through routers or the caller's own program. It does not block a sandwich built from separate transactions (for example a Jito bundle), which the spend cap and `min_action_interval` bound. A wallet that injects its own instructions (for example transaction-guard assertions) cannot be used for public runs.
- Keeper burns and fusions can be sandwiched too, by the keeper itself or by a leaked key: `max_burn_lamports` and `min_action_interval` bound the exposure per action.

## Implementation notes (program `FgAfzGavpUSkhRo1Z1CWuGRrcz1AgZVFrkPeji8DuvWK`)

Where the implementation deviates from or tightens the text above, and why:

- **`initialize_config`** must be signed by the program's upgrade authority (checked against the `ProgramData` account), so the config cannot be front-run between deploy and init.
- **`paused`** blocks exactly three instructions, the ones that create coins or spend a well's SOL on pump.fun / PumpSwap: `register` (new Quantum coins), `quantum_burn` (keeper and public) and `fusion` (keeper and public); each fails with `Paused`. Everything else keeps working so nobody's funds are frozen: `pulse` (fee collection and payouts, owed payments included), `post_entanglement`, `claim_entanglement`, `close_epoch`, `cancel_epoch`, `lock`, `release`, `update_config` and `set_paused`. A pause does not stop the keeper from posting Entanglement epochs; against a leaked keeper key the tools are `cancel_epoch` and rotating the keeper with `update_config`. Only `set_paused` changes it, and every config change bumps `config.version`, which `update_config` must match: an update drafted before a pause (a multisig proposal, a durable-nonce transaction, a second operator) fails with `ConfigChanged` instead of silently unpausing or restoring a rotated keeper.
- **`Quantum`** carries `planned_cliff_secs` / `planned_duration_secs` so the lock terms validated at registration are binding on `lock`, `last_epoch_at` (epoch cadence), `graduated_at` (public Fusion grace) and the owed ledgers. `last_burn_at` / `last_fusion_at` start at `created_at`. `Config` takes `claim_delay` and `version` from its reserved bytes (same size, 8 + 188 bytes).
- **`pulse`** pays nothing that the recipient cannot hold: a payment that would leave a treasury, split or launcher account below its rent-exempt minimum (or an executable account) is not made. Without this, one drained 0-lamport split wallet could block every pulse. The share is owed to that recipient instead (reserved in the well, paid in full together with later shares once the recipient can hold it), so it is never re-split: before the owed ledger, pulsing in small steps while a split wallet was empty moved most of that split's share to the other recipients and paid the protocol cut again. `register` refuses split wallets that could never be paid (see item 3); for a read-only (reserved or executable) split of an older coin the share is left unledgered and re-pulsed, since owing it would lock it forever.
- **Public burns and fusions** read the Instructions sysvar (a named account the client always passes). The keeper's own runs skip that check, so they keep their transaction layout and size (about 33 bytes more than before for the extra account key).
- **`quantum_burn`**: the well WSOL ATA, WSOL mint and SPL Token program are optional accounts, required only for the PumpSwap route (keeps the curve-route transaction small; a curve-route CPI may not touch the well's WSOL ATA then). Besides the spec checks the program requires that (a) a PumpSwap CPI's first account is the coin's canonical pool (`["pool", 0u16, pool_authority(mint), mint, WSOL]`), so the well cannot be made to buy from an attacker's pool, and (b) the well token ATA actually received tokens (otherwise a CPI could route the bought tokens elsewhere). `spent` counts the well WSOL ATA's lamports before and after, so creator fees sitting there are never mistaken for burn spend.
- **`fusion`** takes the canonical pool, its LP mint (`["pool_lp_mint", pool]`) and the well LP ATA (created if needed, under `lp_token_program`) as named accounts; both CPIs must target that pool, and the well LP ATA must receive LP tokens.
- **Client compatibility:** `pulse`'s `rent_payer`, `bonding_curve` and `pool`, `fusion`'s `lp_token_program`, the `instructions_sysvar` of `quantum_burn` and `fusion`, and the `update_config` / `initialize_config` arguments change those instructions, so the program, `shared/idl/quantum_hooks.json` and `shared/quantum.mjs` are deployed together (see `docs/DEPLOY.md`). `buildPulseInstructions` passes its `payer` as `rent_payer` and, until `graduated_at` is set, the canonical pool (or the completed curve). `buildUpdateConfigInstruction` refuses a `paused` field; use `buildSetPausedInstruction`. `buildCancelEpochInstruction({ connection, authority, mint, index })` reads `config.keeper` for the rent.
- **Client account reads** check the owner: `fetchConfig`, `fetchQuantum` and `fetchEpoch` return null unless the address holds an account owned by this program that starts with that account type's discriminator (`isQuantumAccount(info, name, programId)`), and `decodeConfig` / `decodeQuantum` / `decodeEpoch` return null for bytes of another type. Anyone can send lamports to any address, so a closed or cancelled Epoch PDA can come back as a System-owned account with no data; it reads as gone, like a missing account, instead of failing to decode. The well ledger (`fetchWellBalance`, `pendingCreatorFees`), `verifyQuantumCoin().registered` and `buildPulseInstructions` apply the same check to the Quantum and Config accounts.
- **`post_entanglement`** also rejects `total == 0`; proofs longer than 24 nodes are rejected.
- Test builds use the `short-expiry` feature (epochs expire after 20 s and may be posted every 15 s instead of every 20 h) so `close_epoch` and the cadence can be tested on a local validator; production builds keep 30 days and 20 hours. The claim delay is a config value, so tests simply set it small.
